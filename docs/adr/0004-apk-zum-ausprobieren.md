# ADR 0004: APK zum Ausprobieren im Pull Request

Status: angenommen (Plan des Architekten in UCH-50, Story UCH-43, umgesetzt in UCH-54)

Nummer 0004, weil `0003-datenhaltung.md` auf dem Feature-Branch `feature/UCH-38-aufgaben-anlegen` schon vergeben ist. Plan und Issue nennen noch 0003.

## Kontext
Jan soll jedes Feature ausprobieren können, ohne selbst zu bauen. Zu jedem Pull Request mit grüner Pipeline braucht es deshalb eine installierbare APK. Sie soll sich innerhalb eines Pull Requests über die vorige Version installieren lassen, ohne dass die Daten verloren gehen. Dafür braucht es eine gleich bleibende Signatur. Vorgaben: kein Secret, kein Konto, kein Geld (Security `vorgaben` R1, R3), der Workflow behält `permissions: contents: read`, Renovate- und Fork-PRs funktionieren genauso.

## Entscheidungen
1. **Schlüssel je Pull Request im Actions-Cache.** Beim ersten Lauf eines PR erzeugt `tools/ci/tryout-sign.sh` einen RSA-2048-Schlüssel in einem PKCS12-Keystore mit zufälligem Passwort (`openssl rand`), alles unter `$RUNNER_TEMP/tryout-signing`, außerhalb des Checkouts. `actions/cache` legt das Verzeichnis unter `tryout-signing-pr-<N>` ab, ohne `restore-keys`. Caches eines `pull_request`-Laufs sind nur für Läufe desselben PR sichtbar, ein Eintrag ist unveränderlich. Der Fingerabdruck des Zertifikats liegt als `fingerprint.txt` daneben. Bei einem Treffer muss die neu signierte APK genau diesen Fingerabdruck haben. Keystore-Ausgaben gehen nach `/dev/null`, das Passwort wird nur als Datei übergeben und mit `::add-mask::` maskiert.
2. **Release-Build mit R8, nachträglich signiert.** Der Job baut `assembleRelease r8Check` und signiert `app-release-unsigned.apk` mit `zipalign -p 4` und `apksigner`. Der Build-Typ `release` in Gradle bleibt ohne `signingConfig`. `tools/ci/tryout-apk-check.sh` prüft Paket, `minSdk` (aus `app/build.gradle.kts` gelesen, `tools/ci/tryout-min-sdk.sh`), nicht debuggable, Signatur v2, genau ein Signer und den Fingerabdruck.
3. **Installations- und Starttest auf API = `minSdk` vor dem Upload.** Im selben Job, auf genau der Datei, die hochgeladen wird: Emulator API 26 (`target: default`, `x86_64`; `aosp_atd` gibt es erst ab API 30). `tools/ci/tryout-install-test.sh` prüft die API des Geräts, installiert, aktualisiert mit `install -r` und startet die App (gemeinsame Start-Prüfung `tools/checks/app-start-lib.sh`, auch von `app-start.sh` genutzt). Es signiert nie selbst. Der Job `emulator` (API 34) bleibt unverändert.
4. **Ablage.** Job `tryout-apk` nur bei `pull_request`, `needs` auf alle anderen Jobs außer `screenshots` (seit UCH-124: beide sind Belege, ein Screenshots-Job, der wegen der Umgebung rot bleibt, soll Jan nicht die APK nehmen), `concurrency` je PR ohne Abbruch (zwei Läufe erzeugen nie zwei Schlüssel). Upload mit `actions/upload-artifact` v7 (SHA-gepinnt), `archive: false`, `retention-days: 30`, `if-no-files-found: error`, als letzter Schritt vor der Zusammenfassung. Name `uchilab-todo-pr<N>-<7 Zeichen von pull_request.head.sha>.apk` (nicht `github.sha`, das ist der Merge-Commit). Zusammenfassung auf Deutsch mit Link, SHA-256, Fingerabdruck und Hinweis auf einen neuen Schlüssel. Kein Kommentar im PR (bräuchte `pull-requests: write`).
5. **Regeln des Jobs im Review, nicht per Skript** (seit UCH-124, Regel R1a aus UCH-116: keine Prüfung prüft den Text von `ci.yml`). Das gestrichene `tools/ci/tryout-workflow-check.sh` prüfte: nur `contents: read`, kein `secrets.` im Workflow, `if` auf `pull_request`, `needs` auf alle anderen Jobs (aus der Datei gelesen), `concurrency`, kein `continue-on-error`, kein `if` vor oder auf dem Upload, Upload nach dem Emulator-Schritt und mit demselben Pfad, `archive: false`, `retention-days` ≥ 14, `if-no-files-found: error`, danach nur die Zusammenfassung. Dazu der Cache: genau ein `actions/cache`-Schritt vor `tryout-prepare.sh`, Schlüssel exakt `tryout-signing-pr-<N>`, kein `restore-keys`, derselbe Pfad wie das Schlüsselverzeichnis des Prepare-Schritts. Diese Punkte liest der Architekt bei jeder Änderung an `ci.yml` im Review.

## Gegenproben
Seit UCH-124 keine eigenen mehr (R2 aus UCH-116: die APK ist ein Beleg). Geprüft werden Signatur (`apksigner verify` in `tryout-apk-check.sh`) und Installation (`adb install` in `tryout-install-test.sh`), beides Standardwerkzeuge. Die früheren Gegenproben 15a–15f und 16 sind gestrichen, `tools/ci/tryout-emulator-run.sh` ruft nur noch `tryout-install-test.sh` auf.

## Folgen
- Ein PR, der 7 Tage keinen Lauf hatte, bekommt einen neuen Schlüssel (GitHub löscht den Cache-Eintrag). Jan muss dann die alte Version deinstallieren. Gleiches gilt beim Wechsel zwischen PRs. Die Zusammenfassung sagt das fett, das README erklärt es.
- Wer Code im PR ausführen kann, kann den Schlüssel dieses PR lesen. Das ist bewusst getragen: Er bestimmt den Code der APK ohnehin, die Daten sind erfundene Testaufgaben.
- Verworfen: fester Schlüssel als GitHub-Secret. Er beseitigt die 7-Tage-Grenze, ist aber ein neues Secret (Jans Entscheidung, Security R3) und fehlt bei Renovate- und Fork-PRs. Wird die Grenze im Alltag lästig, schlägt der PO das Secret Jan vor.
- Ein zusätzlicher Emulator-Boot (API 26, `default`-Image) hinter allen anderen Jobs verlängert die Laufzeit eines PR.
